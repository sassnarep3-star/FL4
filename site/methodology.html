Methodology

The verification pipeline, the checks that run on every build, and the refusals that define this project's honesty.

How a value gets onto this site

1. Read the official page in full, not a search snippet. The Week 10 availability capture is 8 of 8 chunks of one page; partial reads are what create silent gaps.

2. Transcribe with a fixed rule, not with judgement. The inclusion rule for the player table is 'listed by the club with a game status of Out or Doubtful'. Anyone can re-derive the same 75 rows from the same page; that reproducibility is the only real defence against cherry-picking.

3. Record a source link per row and an as-of timestamp per table. The builder raises an error if a row in a verified table has no source, so an unattributed number cannot ship even accidentally.

4. Re-verify at build time. Nine checks run in CI: the row-level counts are re-tallied against the declared team aggregates; club records on the report are checked against the standings; the standings are checked for conservation of wins against losses across the league; duplicates, fixture coverage and bye patterns are checked; and the strategy/correlation files are checked for any non-null edge or correlation value.

5. Publish the blanks. Where the official page had an empty cell, this site shows a blank, not a guess. Where the whole field is missing (depth, prices), the gap is a row on the Flagged page with the action that closes it.

Deliberate refusals, and why each one is a feature

  • No price data, therefore no edge numbers. F-01. A percentage here would be decoration.
  • No replacement names on the depth page. F-02. The source has no such field.
  • No probabilities attached to Out/Doubtful/Questionable. F-03. The league policy text was not retrieved, and the secondary pages that describe it are not a licence to publish a number.
  • No standings home/road/division splits. F-04. The rendered column order was ambiguous, so the columns were dropped rather than mapped by assumption.
  • No populated leaderboard. An empty board is the correct rendering of a project that has not settled a bet.
  • No re-derivation of a 'sensible' roster. Where the league page lists a player on a club no prior knowledge would predict, the row is transcribed exactly and flagged for human review (F-14). The league filing is the source of truth; my expectations are not. The same page confirms mid-season trades in this window, which is a reminder that season-long priors go stale fast.

Engineering

data/*.json is the source of truth; tools/build_site.py renders every page from it. HTML is never hand-edited, so a correction is a data edit and stays reviewable in a diff. No external fonts, frameworks or CDNs: the page renders with zero third-party requests, all links are relative so the site works under a project-page subpath, and tables are filterable and sortable with about 1 KB of progressively-enhanced JavaScript, so the content is still readable with scripting off.

GitHub Actions runs the builder in check mode (which fails if any generated page would differ, or if a verification check fails), audits internal links, and publishes site/ to Pages. Coordination between parallel agent sessions happens in COORDINATION.md at the repo root, including file-ownership claims so two sessions never edit the same generated artefact.

Reproducibility

To reproduce the injury table from scratch: open the official report, select the season and week, read every chunk, keep rows whose game-status cell is Out or Doubtful, and transcribe player, position, disclosed injury, practice status and game status verbatim. Any independent reviewer should land on the same 75 rows - and if they do not, the difference is itself a data-quality finding worth flagging.

What cannot be reproduced from a page read: any historical series, any price, and anything about who replaced a starter. Those are stated as gaps rather than as results, which is the whole point of this section.
